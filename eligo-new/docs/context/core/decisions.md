## D-001：使用单仓库

- 状态：已采纳，2026-07-29。
- 决策：`eligo-server/`、`eligo-frontend/`、`infra/` 和 `docs/` 使用根目录同一 Git 历史。
- 理由：接口、实现、构建和联调文档可以在同一变更中审查，适合当前前后端各一人的团队。
- 约束：子目录不得再初始化 `.git`；历史后端来源只在仓库文档记录。
- 代价：需要明确 CODEOWNER/审查边界，避免两个开发者互相覆盖。

## D-002：后端采用模块化单体

- 状态：已采纳。
- 决策：一个 Spring Boot 进程、一个主 MySQL，按领域包分模块。
- 理由：MVP 业务强关联、团队规模小、共享事务价值高。
- 替代方案：微服务。
- 未采用原因：会引入服务发现、网关、消息可靠性、分布式事务、链路追踪和多发布单元。
- 演进触发：独立团队/扩缩容/发布需求至少出现两项，再评估物理拆分。

## D-003：OpenAPI 是机器可读接口基线

- 状态：已采纳。
- 决策：`docs/api/openapi.yaml` 只描述当前后端已实现接口；接口变更与实现同提交。
- 人工状态：`docs/api/README.md` 记录前端封装、页面接入和联调级别。
- 理由：避免“后端文档、前端理解、聊天记录”三套契约。
- 门禁：`OpenApiContractTest` 必须通过。

## D-004：当前本地开发不配置 Nginx

- 状态：已采纳。
- 决策：微信开发者工具本地阶段直接访问 `http://127.0.0.1:8080`；H5 通过 Vite `/api` 代理。
- 理由：减少首轮联调变量，直接暴露后端错误。
- 边界：真机、体验版或共享环境前必须配置 HTTPS 域名和 Nginx/等价网关。
- 安全：MySQL、Redis 和 API 当前均只绑定 `127.0.0.1`。

## D-005：MVP 不做聊天

- 状态：已采纳。
- 不做：私信、群聊、活动群、会话列表、消息撤回、已读回执、WebSocket。
- 替代：关注用户/组织；活动变化由系统通知；活动后内容由动态沉淀。
- 防扩散：前端现有 chat 图标只是旧视觉资产，不代表功能范围，后续页面应改为动态/通知语义。

## D-006：MVP 只做免费活动，支付独立预留

- 状态：已采纳。
- 当前：报名不创建订单，不调用微信支付，不产生退款和结算。
- 未来：支付作为独立模块，拥有支付单、回调、退款、对账和结算状态。
- 关键边界：报名记录不是支付记录；未来由“报名资格/占位”关联支付单，不能给 participation 表堆支付字段。
- 理由：支付会扩大主体资质、财务、退款、风控和合规范围。

## D-007：社交闭环为关注、动态和关注流

- 状态：已采纳；活动收藏与活动评论已由 D-021 修订为 M3 扩展实现。
- 可关注对象：用户、组织。
- 动态作者：用户，或有权限的组织成员代表组织。
- 首期：发布、删除/隐藏、作者主页、关注流。
- 仍不做：点赞（活动/动态）和聊天。
- 分页：关注流和作者动态使用不透明游标。

## D-008：个人达人不是独立账号类型

- 状态：已采纳。
- 普通账号获得发布资格后即可成为个人发起者。
- 企业/社团使用组织和组织成员角色。
- 管理员是 authority/角色，不是另一张登录账号表。
- 影响：活动发布主体使用 `ownerType + ownerId` 或等价多态模型，但权限判断必须集中。

## D-009：动态与活动弱关联

- 状态：已采纳。
- 动态可不关联活动，也可带一个可选 `activityId`。
- 活动下架/删除不自动删除作者动态；读取时对不可见活动隐藏卡片。
- 理由：动态属于作者内容，活动只是引用目标。

## D-010：系统通知不是用户消息

- 状态：已采纳。
- 通知只能由受控业务事件或平台产生。
- 用户不能向其他用户提交任意通知正文。
- 站内通知是主能力；微信订阅消息未来作为外部投递适配器。
- 外部投递失败不回滚已成功的核心业务。

## D-011：MySQL 为业务事实

- 状态：已采纳。
- MySQL 保存账号、活动、报名、关注、动态、通知和未来支付状态。
- Redis 只保存 access token 缓存、限流、短期幂等或可重建状态。
- 名额、支付、关注唯一关系不得只依赖 Redis。

## D-012：小程序不作为 Docker 常驻服务

- 状态：已采纳。
- Docker Compose 启动 MySQL、Redis 和 API。
- 小程序在宿主机执行 uni-app 构建，产物导入微信开发者工具。
- 理由：小程序最终由微信工具上传，不是 Web 静态站点；把它做成 Nginx 容器不会完成微信发布。

## D-013：四类产品身份由能力组合产生

- 状态：已采纳，2026-07-30。
- 产品展示：游客用户、认证个人、认证企业用户、管理员。
- 技术实现：由会话、当前协议、个人资料、企业资质、组织成员角色和平台 authority 组合计算 capability，不保存互斥的单一 `userType`。
- 游客边界：未登录或资料/协议未完成的账号只能读取公开内容。
- 企业边界：企业是 Organization，认证个人代表企业操作；企业资质失效只撤销企业能力。
- 管理员边界：`ROLE_ADMIN` 与个人/企业身份正交。
- 详细规则：[用户身份、权限与发布流程规范](../../../../../Eligo-main/Eligo-main/docs/context/core/roles-and-permissions.md)。

## D-014：个人发布与企业发布使用独立命令和页面

- 状态：已采纳，2026-07-30。
- 决策：个人和企业复用活动公共字段、读模型和生命周期，但前端页面、写接口与鉴权入口分开。
- 个人命令从当前 userId 确定主体；企业命令从 organizationId 加成员权限确定主体。
- 理由：避免由客户端提交任意 `ownerType/ownerId`，并让个人轻量表单与企业资质/保障字段清晰分离。
- 约束：支付、退款和结算未重新立项前，企业活动仍只能免费。

## D-015：管理员 UI 暂缓

- 状态：已采纳，2026-07-30。
- 决策：本期不开发管理员页面、完整运营后台或用户端管理员入口。
- 保留：`ROLE_ADMIN` 安全命名空间、企业资质/内容审核状态机、不可变提交快照和审计事件。
- 本地联调：可用受控且可审计的测试夹具/内部操作产生审核结果，不允许普通用户调用，也不能直接覆盖最终状态而不留事件。
- 上线门槛：没有真实审核责任人与受保护审核通道时，企业认证和需人工复核内容不能开放上线。

> 2026-07-30 补充：D-018 将当前企业开发流程改为后端预置数据，不再实现 D-015 中的企业审核状态机和审核夹具；D-015 只保留“管理员 UI 当前不做”的结论。

## D-016：当前只做本地开发，不提供或伪造正式协议

- 状态：已采纳，2026-07-30。
- 事实：项目尚未注册公司，当前不准备上线，数据库没有用户协议和隐私政策正文。
- 决策：`agreements=0` 时登录链按无待同意项继续，不插入临时协议，不生成虚假 consent。
- 保留：既有协议接口和数据模型不删除，未来准备共享测试或上线时重新启用。
- 影响：当前受限操作链为“微信登录 → 资料补全”；IT-001 仍记录协议阶段为空集合。
- 上线门槛：正式法律文本、责任主体、隐私合规和小程序规则评审完成后，才能用新迁移写入生效协议。

## D-017：认证个人完成项与选填资料

- 状态：已采纳，2026-07-30；按已合并后端契约于 2026-08-05 核对。
- 完成判定：姓名、生日、地址、性别、有效电话号和至少一个有效标签。
- 解释：“姓名”当前按展示姓名/昵称处理，不是身份证法定实名；地址沿用省市区；电话通过微信手机号授权绑定；标签至少一个。
- 选填：邮箱、头像、简介。邮箱填写后仍需格式校验、规范化和唯一性保护。
- 明确不做：学生认证、身份证、人脸和年龄资格审核。
- 当前事实：后端迁移/API/完成判定/OpenAPI 已一致；前端资料、手机号、邮箱、兴趣和选填头像代码已接入，端到端联调待完成。
- 迁移原则：后端迁移/API/完成判定/OpenAPI/测试先合并，前端再按契约接入；缺少完成项的用户自然保持资料未完成。

## D-018：企业由后端预置，一个企业一个账号，不做审核

- 状态：已采纳，2026-07-30。
- 决策：本地企业是 `Organization + 唯一 OWNER 用户关系`；每个企业只有一个有效操作账号。
- 建数：后端通过只在 dev/test 生效、可重复执行的种子 SQL 或夹具直接写数据库。
- 不做：企业申请、证明材料、资质状态机、人工审核、成员邀请、多角色、管理员审核页。
- 权限：只有 `DEV_ENABLED` 企业的唯一 Owner 获得企业发布能力；禁用关系只撤销企业能力。
- 对外表达：本地页面只能标“开发测试企业”，不能显示“官方认证”等真实背书。
- 未来：共享测试或上线前重新立项企业主体、审核责任和内容安全。

## D-019：个人发布比企业基础页增加报名详情和活动留言

- 状态：已采纳，2026-07-30。
- 决策：企业发布定义基础活动字段；个人发布复用这些字段，并额外增加“报名详情”和“活动留言”。
- 技术边界：个人/企业使用独立页面、命令和鉴权；公共字段可复用 DTO 组件，但不能接受任意主体。
- 待编码评审：两个个人专属字段的字数、是否必填和可见时点。
- 当前审核：本地没有人工审核；服务端权限和字段校验通过后直接持久化并发布。

## D-020：报名直接成功，发起人不占名额

- 状态：已采纳，2026-07-30。
- 决策：认证个人报名通过会话、资料、活动状态、时间窗口和名额校验后，直接写入 `ACTIVE`。
- 不做：报名申请、发起人审批、`PENDING/APPROVED/REJECTED` 报名状态。
- 名额：活动发起人不自动报名，不计入 `participant_count`。
- 并发：直接成功不等于取消幂等和名额约束；同一用户重复请求返回同一有效结果，最后名额并发不能超卖。

## D-021：活动收藏与评论进入 M3；坐标系统一 GCJ-02 不落库

- 状态：已采纳，2026-08-22。
- 活动收藏：`activity_favorites` 表 + 收藏/取消/状态/本人列表，账号注销时清理关系。
- 活动评论：`activity_comments` 表 + 顶层留言/一层领队回复/软删除占位/作者幂等；仍不支持动态点赞与聊天。
- 关系：D-007 首期“不做评论/收藏”的结论由本决策修订为 M3 扩展；点赞与聊天仍不在当前范围。
- 坐标系：活动集合地点坐标统一使用 `GCJ-02`（国测局坐标系，目标端为微信小程序地图）。
  - 写入时只接受 `GCJ-02`（有坐标省略时默认 `GCJ-02`，无坐标必须为空）；读响应在坐标完整时返回 `coordinateSystem=GCJ-02`；
  - 当前 `activities` 表**不新增坐标系列**，存储坐标即 `GCJ-02`，由写请求校验保证不变量，避免保存恒为 `GCJ-02` 的冗余常量列；
  - 未来若需支持其他坐标系（WGS-84/BD-09）再重新立项并评估落库迁移，当前派生与写校验结构无法表达“该行坐标是其他坐标系”。
- 来源约束：前端定位/地图选点必须显式使用 `GCJ-02`（`wx.getLocation` 需传 `type:'gcj02'`），否则会把 WGS-84 当作 GCJ-02 入库；建议保留后端大陆范围粗校验作为最后防线。

## D-022：使用 Kotlin 重写后端

- 状态：已采纳，2026-09-13。
- 决策：将 eligo-main 的 Java 后端使用 Kotlin 2.1.21 重写为 eligo-new，保持相同的 Spring Boot 4.1.0、相同的 OpenAPI 契约（65 条路径、80 个 HTTP 操作）、相同的数据库 schema 和相同的 Flyway 迁移脚本（V1–V18）。
- 理由：Kotlin 的空安全、简洁语法、`data class` 和更好的 DSL 支持可以提升开发效率，同时保持与 Java 的完全互操作性。Kotlin 的非空类型系统在编译期消除大量空指针风险，`data class` 减少样板代码，`jackson-module-kotlin` 提供更自然的 Kotlin 序列化支持。
- 约束：
  - 必须与 Java 版本保持 100% API 兼容；相同的 OpenAPI 契约是唯一接口事实来源；
  - 相同的数据库 schema，相同的 Flyway 迁移脚本，不新增或修改已有迁移；
  - 相同的测试覆盖范围，业务规则、并发、安全和契约测试不降低；
  - 源码根目录为 `src/main/kotlin/com/eligo/server/`，按领域顶层包组织；
  - eligo-new 仅包含后端，前端仍由 eligo-main 仓库维护。
- 代价与取舍：
  - 构建工具从 Maven 切换为 Gradle（Kotlin DSL），通过 Gradle Wrapper 统一版本；原 Maven Wrapper 不再使用；
  - 测试框架使用 mockito-kotlin 5.4.0 替代 mockito-java；Mock 创建使用 `org.mockito.kotlin` 命名空间，参数匹配器使用 `any<T>()`、`eq()`、`anyOrNull()`，打桩使用 `whenever(...)` 替代 `` `when`(...) ``；
  - Jackson 模块从 `jackson-module-parameter-names` 切换为 `jackson-module-kotlin`，由 Spring Boot 自动配置；DTO 字段校验注解必须使用 `@field:` 前缀，可空字段使用 `String?` 等可空类型；
  - 领域对象优先使用 `data class`，配置属性使用 `@ConfigurationProperties` 绑定的 `data class`；
  - Service 接口与默认实现以 `Default*Service` 命名。
- 不变：
  - 模块化单体架构不变；
  - 四类产品身份、权限矩阵、发布流程和报名规则不变；
  - MySQL 为业务事实、Redis 不承载最终一致性的原则不变；
  - 本地开发不配置 Nginx 的决策不变；
  - 当前只做本地开发、不提供正式协议的决策不变。
- 演进关系：D-001 至 D-021 全部仍然适用；eligo-new 是 eligo-main 的目标版本，Java 版本不再演进新功能。前端、Docker 基础设施和跨模块文档仍由 eligo-main 仓库维护，eligo-new 通过相对路径引用。
